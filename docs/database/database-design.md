# LMSys Market
## Modelagem Inicial do Banco de Dados

**Documento:** Database Design  
**Versão:** 0.1  
**Status:** Modelagem inicial  
**Produto:** LMSys Market  
**Banco de dados:** PostgreSQL  
**ORM:** Entity Framework Core

---

# 1. Objetivo

Este documento define a modelagem inicial do banco de dados do **LMSys Market**.

O banco deverá suportar as principais operações de um supermercado:

- empresas e lojas;
- usuários e permissões;
- produtos;
- categorias;
- marcas;
- códigos de barras;
- preços;
- estoque;
- lotes;
- fornecedores;
- compras;
- clientes;
- vendas;
- pagamentos;
- caixas;
- promoções;
- inventários;
- perdas;
- financeiro;
- auditoria.

A modelagem deverá priorizar:

- integridade;
- desempenho;
- rastreabilidade;
- histórico;
- concorrência;
- expansão futura;
- suporte a múltiplos terminais;
- futura utilização por múltiplas lojas.

# 3. Convenção de nomenclatura

```text

```


Colunas:

```text
product_id

sale_price

```

---

# 4. Chaves primárias

A maioria das entidades utilizará:

```text
bigint
```

como identificador.

Exemplo:

```sql
id bigint generated by default as identity
```

Motivos:

- alto volume suportado;
- índices menores que UUID;
- excelente desempenho;
- facilidade de utilização;
- simplicidade operacional.

GUIDs poderão ser adotados futuramente quando houver necessidade real.

---

# 5. Datas e horários

Datas e horários operacionais deverão utilizar preferencialmente:

```text
timestamp with time zone
```

No PostgreSQL:

```text
timestamptz
```

A aplicação deverá tratar corretamente o horário local apresentado ao usuário.

Exemplos:

```text
created_at
updated_at
opened_at
closed_at
sold_at
paid_at
```

---

# 6. Valores monetários

Valores financeiros deverão utilizar tipos de precisão fixa.

Padrão inicial:

```text
numeric(18,2)
```

Exemplos:

```text
sale_price
total_amount
discount_amount
payment_amount
```

Custos que possam exigir maior precisão poderão utilizar:

```text
numeric(18,4)
```

---

# 7. Quantidades

Produtos vendidos por unidade ou peso exigem suporte a casas decimais.

Padrão inicial:

```text
numeric(18,3)
```

Exemplos:

```text
quantity
current_quantity
minimum_quantity
```

Assim será possível trabalhar com:

```text
1 unidade
2 unidades
0,350 kg
1,250 kg
```

# 32. Quantidade disponível

A quantidade disponível poderá ser calculada por:

```text

quantity - reserved_quantity
```

A primeira versão poderá não utilizar reserva efetivamente.

O campo será mantido como possibilidade de evolução.

# 33. Concorrência do estoque

A tabela:

```text
inventory_balances
```

será uma das áreas mais sensíveis do sistema.

Ela poderá utilizar:

```text
version
```

como controle de concorrência otimista.

Isso ajudará a evitar situações onde dois processos atualizem a mesma quantidade sem detectar conflito.

A estratégia final será implementada no módulo de estoque.

# 75. Estratégia de exclusão

Foreign Keys não utilizarão `CASCADE DELETE` indiscriminadamente.

Por exemplo:

```text
Product
 ↓
SaleItem
```

não deverá permitir apagar todas as vendas antigas apenas porque alguém tentou remover um produto.

Na maioria dos cadastros históricos:

```text
DELETE
```

será substituído por:

```text
is_active = false
```

# 76. Venda como registro histórico

Após a venda ser concluída, suas informações deverão ser preservadas.

O sistema não deverá depender do cadastro atual do produto para reconstruir valores históricos.

Por isso:

```text

```

armazenará informações como:

```text
product_description
unit_price
discount_amount
total_amount
```

---

# 77. Compras como registro histórico

O mesmo princípio será aplicado às compras.

O custo utilizado no momento do pedido e do recebimento deverá permanecer disponível mesmo que o custo atual do produto seja alterado posteriormente.

# 110. Regra de integridade histórica

Nenhuma funcionalidade deverá destruir informações necessárias para compreender uma operação passada.

Exemplos:

Uma alteração do produto não poderá mudar vendas antigas.

Uma alteração de preço não poderá modificar o preço registrado em vendas anteriores.

Um usuário desativado continuará aparecendo como responsável por operações anteriores.

Um fornecedor desativado continuará associado aos pedidos realizados anteriormente.

---

# 111. Regra de desempenho

O banco deverá favorecer tanto:

```text
consulta rápida do estado atual
```

quanto:

```text
rastreabilidade histórica
```

Por isso utilizaremos estruturas como:

```text
inventory_balances
+
inventory_movements
```

em vez de recalcular permanentemente todo o estoque através do histórico.

---

# 112. Regra de auditoria

Auditoria não substituirá as tabelas operacionais.

Por exemplo:

```text

```

continuará possuindo seu próprio histórico.

O:

```text
audit_log
```

registrará ações administrativas ou alterações importantes.
